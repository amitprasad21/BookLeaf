# BookLeaf: approach and tradeoffs

BookLeaf gives authors a clear view of their books, royalties and support conversations, while operations staff work a prioritised queue. Two Next.js portals share one Express/TypeScript API and Supabase Auth/Postgres. Shared contracts and UI components keep the two experiences consistent. The provided ten-author, eighteen-book dataset is preserved exactly, including missing values.

The core support flow was built before AI. A ticket is stored first; classification runs in the background. Staff can filter and assign tickets, override category or priority, add private notes, and send replies. Optimistic version checks prevent silent overwrites. Server-sent events carry identifiers rather than conversation text; clients re-fetch authorised data. Author responses use explicit serializers, API requests verify identity and role, and database row-level security enforces ownership beneath the API.

AI proposes a category, priority and editable reply. Gemini Flash-Lite is the configured primary and Groq is the bounded fallback. A small, versioned knowledge base is selected by category rather than vector search: its size and clear category mapping make deterministic selection simpler to inspect and test. Facts are calculated in code from the ticket author's records. Payout facts separate a strictly passed deadline from the next scheduled payout; a total pending balance is never treated as a quarterly ledger. The system has no authoritative production completion estimate, so drafts request confirmation instead of inventing one.

Schema checks, one repair attempt, priority floors, draft-policy guards, amount/date warnings, reuse by context hash, daily token limits and circuit breakers constrain model failures. An eight-second provider gate also spaces calls and retries. This trades latency for fewer free-tier bursts. These controls do not prove semantic correctness or guarantee provider quotas: staff must review every draft, and only their explicit action sends it. Manual ticket handling remains available when AI is disabled or unavailable.

Verification includes 375 backend tests and 66 frontend logic tests, passing format/lint/API/type checks and production builds. Approved live triage achieved 36/36 category and priority matches and passed three injection cases. The latest eight draft cases returned answers with 48/49 automatic checks and no amount/date warnings; manual inspection found the earlier completed-action and missing-apology issues corrected in those samples. The outstanding rubric item asks for a production timeline that BookLeaf has not supplied; the user accepted confirmation-pending behavior. These are bounded evaluation results, not a guarantee for arbitrary tickets.

Release work remains explicit: the full signed-in accessibility/browser matrix, independent human security review, hosting access and deployed smoke checks are outstanding. A development-only lint dependency has an unpatched braces advisory; the production audit was clean. Render/Vercel configuration and deployment instructions are prepared, but no live URLs exist yet. The backend intentionally runs as one instance because its event hub, pacing and request limits are in memory. Durable queue infrastructure, uploads, author follow-up messages and usage dashboards are deferred extensions.
